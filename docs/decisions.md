# social

Working name. Git-based posting and overview of everything sent out: social posts, newsletters, blog. Runs on a Cloudflare Worker with a cron every minute. No SQL database.

## Code map

Everything is TypeScript run by Node (`node --test src/`, no build step for `src/`), the app is Astro. One file per idea; fewer, bigger files over many tiny ones.

- `src/` core, framework-free (browser-safe unless it imports `node:`): `types` (shared types, `PLATFORM_LABEL`), `time` (Amsterdam dates: `ymd`, `clock`, `parseDate`, `whenLabel`), `text` (`sentence`, titles), `frontmatter` (read and edit the properties block and the raw file: `readFields`, `with*`), `mentions` (`[[Name]]` and `@Name`, `Entity`), `entities` (loads `entities/`), `preview`, `plan` (late rule, `due`, `readiness`), `channels` (loads `channels.yml`, `resolveName`), `posts` (parses and reads posts), `ideas` (the idea bin: create, save, status, delete), `calendar` (pure view models for List and Calendar), `campaign` (a post folder: load, save with the planning gate, create, add and delete variants), `content-store` (disk behind an interface), `media` (image upload checks), `state` (post state and its file store), `run` (the post run), `remind` (Telegram reminders), `linkedin` (the provider), `connect` (LinkedIn OAuth, `sendProblem`, avatars refresh), `avatars`, `secrets` (tokens and app credentials, private files outside the repo), `ship` (the only CLI: dry run and `--live`).
- `app/` Astro UI: `pages/` (routes, form posts and `api/`), `components/`, `layouts/` (`Shell` the page with the sidebar, `App` the calendar views), `lib/` (`data.ts` server data and shared stores, `ui.ts` small view helpers, `connect.ts` the OAuth flow state), `scripts/` (browser code: `editor`, `autocomplete`, `toast`, `page`, and `dom.ts`, a tiny `h()` element builder).
- Tests sit next to the code as `*.test.ts`.

## Content

- A channel is one connected place to post (an entry in `channels.yml`: Jeroen on LinkedIn, Pop-Up City on Instagram). The word is Channel everywhere: the file, the code, the UI and the CLI.
- No backwards compatibility unless the user asks for it: renames and format changes do not get migrations, fallbacks or old-name aliases.
- `posts/<date>-<slug>/<channel>[-<type>].md`, one file per channel variant. Images sit next to the files.
- The channel is the longest prefix of the file name that exists in `channels.yml`; the rest is the type (`story`). No match is an error. No channel name may be a prefix of another.
- Every file stands alone. No shared base file, no inheritance.
- `status` is `draft` or `planned`; missing means `draft`. Only `planned` posts. The system adds `posted`, `posting`, `reminded`, `failed` and `unconfirmed` in the state, never in the file (renamed from `planned` on 2026-11-18, no compatibility).
- `date` has no offset and is read as Europe/Amsterdam (Obsidian writes it that way).
- Frontmatter stays flat so Obsidian Properties can edit it.
- LinkedIn organization mentions work in personal posts with `w_member_social` (tested 2026-11-12), but the name must match the page's spelling exactly, case included: "Pop-Up City" linked, "Pop-up City" was posted as plain text without an error. The entity note's file name carries the right spelling; the tool cannot check it against LinkedIn.
- An empty text is allowed in a draft (a new post starts that way) and is only an error once the post is planned and not `manual`. User-visible messages avoid developer words: the block between the two `---` lines is called the properties (the Obsidian word), the text is the text, and every message is shown through `sentence()` (`src/text.ts`) so it starts with a capital and ends with a full stop.
- The body is plain text. `**` and `![[` are refused; platforms do not render markdown. `[[Name]]` is the only link form: it resolves case-insensitively to `entities/Name.md`, and the note's file name is used as the display name, so the casing is always right. Per platform it becomes a LinkedIn mention (`linkedin: urn:li:person|organization:...` in the note), an Instagram `@handle` (`instagram:` in the note), or the plain name. An unknown `[[Name]]` is an error. Aliases and headings are not supported. Every plain occurrence of an entity's name in the same post is tagged on LinkedIn, not only the linked one.
- `manual: true` is not posted. It shows in the calendar and sends a Telegram reminder once (state `reminded`, at-least-once, only `planned`, only within 24 hours of its `date`); the post is made in the platform app (story with link sticker). The scheduler sends reminders with `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`; a dry run previews the message.
- One post per channel per folder.
- A due post more than an hour past its `date` is never posted late: it is skipped and reported (`LATE`). Posting a stale post is worse than missing one.

## State and tokens

- State lives in git, on a bot-owned `state` branch, one JSON file per post and channel. `main` is never written by the bot.
- `StateStore` (`src/state.ts`) is the interface: `get`, `create` (create-if-absent), `replace`. `fileStore` writes `posts/<folder>/<variant>.state.json` next to the post it belongs to (2026-11-25: state moved out of `.state/`, so renaming or deleting a post folder takes it along and nothing is left behind; deleting a variant removes its state file) and is the local implementation; the GitHub one is not built yet.
- States: `posting` -> `posted`, `failed` (invalid content or config; nothing posted) or `unconfirmed` (may be live). `failed`, `unconfirmed` and a `posting` older than 10 minutes are reported and never retried automatically; deleting the state file allows a retry.
- `run` (`src/run.ts`): for each ready post without state it validates, claims, posts and completes. `transient`, `rate` and `auth` errors mean nothing was posted, so the claim is removed and the next tick retries; the one-hour late rule caps the retries. Any unexpected error counts as `unconfirmed`. Validation problems leave no state and are reported on every run until fixed. `dryRun` validates only.
- **Delete from the platform (built 2026-11-19, untested against the platforms):** `Provider.remove` exists for LinkedIn (`DELETE /rest/posts/<urn>`, a 404 counts as gone) and Facebook (`DELETE /<post id>`); Instagram's API cannot delete media, so no button. `unpost` (`src/unpost.ts`) needs a `posted` state, calls the provider and writes the state `deleted` (not removal: the post file is still `planned` and would post again). The post page shows "Delete from LinkedIn" for a posted variant, with a confirmation. A `deleted` card shows a neutral Deleted chip.
- The lock is create-if-absent through the GitHub contents API: a 422 means another run has it.
- Write `posting` before the platform call and record the platform id at the moment the post exists (checkpoint). A `posting` state that stays means unknown, never a blind retry.
- Tokens are written at runtime (refresh), so they live in one KV key or an encrypted R2 object, not in Worker secrets.
- Locally, tokens live in `$BOMBARIE_TOKENS` or `~/.config/social/tokens.json` (outside the repo, mode 600; a file readable by others is refused). The `/channels` page lists the status and has Disconnect (removes the token); there is no token CLI, a token only arrives through Connect. An expired token fails the post with a clear error instead of calling the API.
- Connecting a LinkedIn channel happens in the browser on `/channels` (see Connecting in the browser under Editor). It saves the token, writes the person URN from `/v2/userinfo` into `channels.yml` and downloads the avatar; it refuses organization channels and a login that does not match an existing `urn`. Scopes: `openid profile w_member_social`.
- Instagram needs a public image URL: copy to R2 under a hash name, serve from a public domain.

## Overview

- Instagram and Facebook posts made elsewhere are imported by polling; stories only live 24 hours, so poll hourly and keep a copy.
- LinkedIn own posts cannot be read with `w_member_social`; those stay `manual`.
- RSS import is the cheapest adapter (Substack, blog, podcast).
- Substack has no public API for Notes. Posting would use the unofficial session-cookie endpoints (fragile, terms risk); Substack's own Notes scheduler exists since March 2026. Read it through RSS only.

## Direction (decided 2026-11-17; the editor and the local parts are built, the hosted parts are not)

- **Audience:** technical social media managers and makers: developers and devrel, indie founders, people who already live in Markdown, Obsidian, Astro content collections and git. Not non-technical managers: they choose Buffer or Planable for approval flows, and the product does not compete there. Positioning: the light, git-native counterpart of Postiz (which needs two Postgres databases, Redis, Temporal and Elasticsearch to self-host), with blog and newsletter in the same overview. Needs no approval workflow, no analytics, no newsletter editor.
- **Order of delivery (changed 2026-11-19):** a Node app in Docker first, for self-hosting and for Jeroen's own use on his VPS; then see whether there is demand. The landing page gets a "tell me when hosted exists" form: it is the one direct signal for hosted demand. A Cloudflare Worker target is a later, lighter variant and only if there is demand. Why Docker first: the core already runs on Node and reads from disk, Instagram needs a public image URL and JPEG (a container serves it itself and converts with `sharp`), the timer runs in the process, and the Worker route needed a rewrite of almost every layer. The EUR 0 constraints below existed only for self-hosters on the free Workers plan; a hosted service would pay the 5 dollars of Workers Paid anyway.
- **Tenant-aware from day one:** every key, token and index is scoped to the GitHub installation id, so a single-tenant install is just one tenant and hosted needs no rewrite.
- **Cost target:** one small VPS, no other service. The Cloudflare Free limits (10 ms CPU, 50 subrequests, 5 crons per account, KV write cap) only apply if a Worker target is built later; then: no polling, a push webhook updates a compact index of due times, sessions are an encrypted cookie, no `sharp`, state in git. Do not rely on ETags: installation tokens rotate hourly.
- **Pages CMS model, taken in part:** a GitHub App; login with the GitHub user token; unattended work (cron, posting) with the installation token; configuration in the content repo (`channels.yml`, like their `.pages.yml`); saving a post is a commit authored by the user, not the bot. Not taken: PostgreSQL, Next.js, e-mail invitations for people without GitHub (everyone has a GitHub account here). Pages CMS has nothing running in the background, so it has no state branch; ours exists because posting writes state, and that must not pollute `main` or trigger deploys.
- **Two repos:** the product (app code, ours) and the user's content repo (`posts/`, `entities/`, `channels.yml`). Today they are one; they split for the product. A second, read-only repo can be linked later for the articles of an Astro site.
- **Platform apps:** self-hosters create their own. Meta: an app in development mode serves the people who have a role on it, on their own Meta accounts, so no App Review; whether `instagram_content_publish` posts in development mode is unverified, test it with a spike on a real account. LinkedIn: every developer app must be tied to a Company Page, even for personal posting, and "Share on LinkedIn" (`w_member_social`) may be instant or by request (sources differ); posting as a company needs the reviewed Community Management API and is out of scope. A hosted version could share one LinkedIn app; undecided. The connections wizard (steps, fixed callback URL, test button, clear errors) is part of the product because creating a Meta app is hard even for developers.
- **Running it (Docker):** `docker build -t bombarie .` (the design system is the workspace package `@popupcity/ui` in `packages/ui` (named so since 2026-11-27: this repo is public, and plain `ui` did not read as our own set; `ui` in these notes means it), a copy of the components and the `social` theme from the private `ui` repo, so the build needs nothing outside this repo) or `docker compose up` with `BOMBARIE_USERS`. Volumes: `/data` is the content repo (`posts/`, `entities/`, `channels.yml`, plus `.state/_feeds/`), `/config` holds `tokens.json` and `apps.json`. The app must sit behind an https reverse proxy that sends `X-Forwarded-Proto` and `X-Forwarded-Host` (`security.allowedDomains` trusts them for https only); the Meta redirect URL is then simply `https://<domain>/channels/callback` and the relay page on popupcity.net is not needed. In production the app refuses to serve (503) until `BOMBARIE_USERS` is set (`name:password` pairs, comma separated, so no comma in a password; multi-user option 1, 2026-11-24: everyone sees and may do everything, no roles); sessions are an HMAC-signed `bombarie_session` cookie carrying the name (30 days, `src/auth.ts`, the whole `BOMBARIE_USERS` value is the key, so changing any user signs everyone out; the middleware puts the name in `locals.user`); `/login`, `/public/` and `/healthz` are the only open routes; failed logins wait one second. The built assets live under `/assets/` (`build.assets` in `astro.config.mjs`, not Astro's default `_astro`); the node adapter serves them before the middleware, so the login page gets its CSS without a session. `/healthz` is what the Docker healthcheck calls, which also starts the in-process scheduler (`ensureScheduler` runs on the first request). `pnpm dev` needs no password unless `BOMBARIE_PASSWORD` is set. Local dev also runs the scheduler, so a planned post that is due does post.
- **Build order:** the editor against the local disk (`BOMBARIE_ROOT`, done); a `ContentStore` interface with a file implementation (done); Docker image, login and an in-process timer; a public media route for Instagram and the Instagram provider; git sync of the content repo (clone on a volume, pull on webhook or timer, commit and push on save; a failed rebase refuses and reports, never overwrites); GitHub login and App; the connections wizard (LinkedIn done locally, Meta not).
- **Open decisions:** the licence before any release (AGPL keeps the option of being the hosted service yourself, MIT allows competing hosted copies), the name (needed for the repo and README, not for a domain; the GitHub App name is visible to users at login), LinkedIn shared or own app, and the Meta posting spike.

(4) Long operations are asynchronous (built 2026-11-19): Post now returns at once. `startPostNow` (`app/lib/data.ts`) runs `runNow` in the background and answers as soon as the post is claimed (`onClaimed` hook in `src/run.ts`; a post that never starts, such as an invalid or already claimed one, answers with its reason right away); the claim writes the `posting` state, providers report steps through `context.progress` (kept in memory in `src/progress.ts`: "Instagram is processing the image…"), and the page polls `GET /api/state/<folder>/<variant>` every two seconds while `data-posting` is set (a `posting` state younger than 10 minutes), then reloads with a toast (`toastAfterReload` through `sessionStorage`). An outcome that leaves no state file (a retryable error, an invalid or skipped post) is remembered in memory for two minutes and shown once, either by the poll or, when the page loads after the post already finished, as a toast on load. This is because the Cloudflare tunnel cuts a request at about 100 s and an Instagram post can wait 60 s for its container; a waiting request would show a false error while the post goes live. Checked end to end against LinkedIn with a deliberately invalid token (redirect in 24 ms, steps, then the real 401 as the outcome); never against a successful post. (5) Done: the toast. Not doing: skeletons for whole pages, streaming and a slimmer Calendar, until they grow or GitHub data arrives.

The LinkedIn provider follows the Videos API and CogSend's `linkedin.ts`: `initializeUpload` with `fileSizeBytes`, one PUT per `uploadInstructions` range (`videoInstructions` refuses gaps and overlaps) collecting the `etag` of each part with its quotes stripped, `finalizeUpload` with `uploadedPartIds` in order, then polling `GET /rest/videos/<urn>` every 3 s for up to 3 minutes until `AVAILABLE` (a still-processing video is a `transient` error, so nothing is posted and the next tick retries; `PROCESSING_FAILED` is `invalid` with LinkedIn's reason), then `content.media.id`. Facebook refuses a video in `validate`. **Instagram video (built 2026-11-23, tested with mocks, never against Meta):** one MP4 is a Reel (`media_type=REELS`, `video_url`, `share_to_feed=true`, the caption, and the poster frame as `cover_url` when it exists) and in a `-story` variant a video story (`media_type=STORIES`, `video_url`, no caption, no cover); Instagram fetches the file from `<public address>/public/<signature>/mp4/<folder>/<file>` (`publicPath`, `context.publicVideo`, the `/public/` route answers range requests), the container is polled every 5 s for up to 5 minutes (`transient` when it is still working, so nothing is posted and the next tick makes a new container) and `ERROR` is `invalid` with Meta's reason; one video per post, never mixed, no PDF. The editor accepts MP4 on Instagram variants and a variant copied to Instagram keeps the video. The browser draws a poster frame at one second (`app/scripts/videocover.ts`) and stores it as `<video>.cover.jpg`, like a PDF cover (`needsCover`, `coverLabel` and `mediaKind` in `src/types.ts` cover both); tiles, preview, List and peek card show the poster with a Video chip and the lightbox plays the file. `/img` answers range requests (206) so a video can seek. Not built: Reels, thumbnails or captions chosen by the user, conversion (ffmpeg stays out of the image on purpose), streaming slices instead of reading the whole file.

- **Threads (built 2026-11-23, tested with mocks, never against Meta):** a `threads` platform with the Threads API (`graph.threads.com/v1.0`, `src/threads.ts`). **Connect:** its own Threads app ID and secret (not the Meta app's), the authorize URL `threads.com/oauth/authorize` with the scopes `threads_basic,threads_content_publish`, the code becomes a one-hour token and then a 60-day token (`th_exchange_token`), the username and the user id are saved (the username becomes the channel's `handle`; a login that is another account than the handle is refused); the scheduler renews a token in its last 14 days (`th_refresh_token`, `refreshThreadsTokens`). **Post:** a container (`TEXT` with the link as `link_attachment`, `IMAGE`, `VIDEO`, or a `CAROUSEL` of 2 to 20 pictures), polled until `FINISHED` (a video up to 5 minutes), then `threads_publish`; media come from the public address of the app like Instagram's (`publicImage`, `publicVideo`). 500 characters, text or a picture, one video and not mixed, no PDF, no story. **Not built or unverified:** deleting (the endpoint exists but `threads_delete` is not in the documented scopes, so there is no Delete from Threads button), mentions (the API docs say nothing about `@name` linking, so a name is plain text), and whether an app in development mode may post: it can only post for **Threads testers**, so add your own account as one (App roles in the Meta dashboard, then accept it in Threads under Website permissions).

## Planned: blog and newsletters in the overview (not built)

- Goal: see website posts and newsletters next to the social posts, per campaign folder. Planning stays in the platform itself (WordPress, Substack, the newsletter tool); we plan a slot and confirm it afterwards.
- A planned blog or newsletter post is a `manual: true` file in the campaign folder (the file name is the channel, optional `title`, `slug` or `url` as match hints, no body needed). It shows in the calendar and sends the existing Telegram reminder.
- A channel gets a `feed:` URL and a platform kind for the channel (`blog`, `newsletter`, `podcast`). A feed adapter reads the public feed; no credentials are stored, so hosting needs no secrets for these channels.
- Reconciler (one pure, tested function): observed items (feed `guid`, absolute post time, title, link) and open manual plans go in, matches come out. A match needs the same channel and a time window around the planned `date` (about 12 hours; compare absolute instants, the feed is UTC and `date` is Europe/Amsterdam). Inside the window the title (or `slug`/`url` hint) wins, otherwise the nearest unique item. Two candidates or no clear winner means no automatic match: the feed item shows as its own card with a "this is it" action and the plan stays open.
- A match never deletes or edits the plan file (`main` is never written by the bot). It writes a `posted` state on the `state` branch with `url`, the feed `guid` and `matched: feed`, and the calendar shows one card. Deleting that state file undoes a wrong match, as with `failed`.
- Every seen feed item is stored as a small file on the `state` branch, because feeds only keep their latest 10 to 20 items and dedupe must stay stable. Unmatched items show as `posted` cards.
- A plan that is past its time and not matched becomes a notice ("planned, not seen in the feed").
- The same reconciler later confirms Instagram and Facebook posts that are imported by polling (stories included).
- Limits: newsletters sent only through a tool without a feed (Sendy, Brevo) stay reminder-only; whether their web archives offer a feed is unchecked. Substack has no planning API, but its newsletters appear in its RSS.
- Posting through APIs comes later and only where the platform plans natively, so it executes the send and we only hand over the time: WordPress `status: future` with an Editor or Admin application password (an Author is silently downgraded to a draft; wp-cron can run late), Brevo `plannedAt` (test it, one report says API campaigns can land on "running"), a site in git with a deploy hook fired by our cron. Sendy's API planning is unchecked.
- A newsletter send is irreversible, so the one-hour late rule does not apply to it: it needs explicit approval at the moment itself or a test send, never an automatic late send.
- The platform owns the content, we own the plan: pull status for display, write back only a date the user changed in our UI. No newsletter editor and no email rendering; the newsletter tool keeps its templates.
- Order: channel kind and `title` on manual cards, then the feed adapter with the reconciler, then one API connection for the tool actually used.
- **Built 2026-11-19 (first step, no reconciler yet):** a channel takes `feed:` (https, public host only, `feedUrlProblem` in `src/feed.ts`; set on the channel page of a Substack or Website channel, "Save and read"; `website` is a feed-only platform with an RSS mark (the bare Phosphor bold arcs in white on an ink tile, the same tile and glyph size as the other marks), any RSS or Atom address works, checked against a real WordPress feed). `fetchFeed` reads RSS or Atom (small regex parser, no dependency; redirects followed by hand and re-checked, 8 s, 2 MB), `refreshFeeds` runs in the scheduler tick at most once an hour per channel, and every item ever seen is kept in `.state/_feeds/<channel>.json` (feeds only keep their last 20 or so; a failed read keeps what was stored and records the error). Stored items of the last 365 days show as `posted` cards (`FEED_DAYS` in `src/calendar.ts`; the popupcity.net radar feed has 1300 items back to 2013 and the views would otherwise reach back to then; older items stay stored, an archive page is not built) with an `url` (`CardModel.url`: the card links out, has no menu, cannot be moved or deleted). Not built: matching a planned manual post to a feed item, DNS-rebinding protection (the address is typed by the logged-in user).

Hairlines and hover/today states are `ring-*` utilities (`ring-line`, `hover:ring-ink/20`, `ring-ink`), so the status chips, cards and buttons have no lift or glow.

Anything clickable has `cursor-pointer` on the element or in its component's variant, never in `global.css` (which stays as empty as possible): buttons, `summary`, labels around a checkbox, radio or file input, and the inputs themselves; links need none (house rule 12 in `ui`).

### Editor (designed 2026-11-17; all slices built, with an Edit and a Source view)

- **A page, not a modal or drawer** (agreed). `/posts/<folder>` is one page per campaign with the channel variants as tabs. Why: writing a post takes minutes with unsaved text, an uploading image and an open `[[` completion; a modal that is big enough is a page with a backdrop, loses work on Esc or an outside click, and has no URL or back button. A page has the room for text and preview side by side, a shareable URL, and costs no script to open or close. The one loss is context, so the back link goes to `/#<day of the post>` instead of relying on the browser's scroll restoration, which our scroll-to-today would break. Reconsider only if a small "peek" for quick actions (change a time, plan) proves to be needed.
- **A document, not a form, in two views (decided later, see below):** Edit is a plain textarea with a row of fields above it (date, `manual`, status), Source is the whole file as text. No toolbar and no Markdown preview: the body is plain text and `**` is refused. Rich text with inline mention chips (contenteditable) was weighed and left out; the side preview already is the WYSIWYG result.
- **Layout of the post page (restructured 2026-11-17):** a header with the campaign title, the status chip and the date as its identity, then the variant tabs; below it two columns (3 to 2): Write (a large textarea with the Edit and Source toggle above it, Save as the secondary button and the status line below) and, to the right, the Preview as an output panel (a tinted surface holding a post-shaped white card with the avatar, name and the text) above the Plan block (date, the reminder-only checkbox and one full-width primary button, Approve or Back to draft). Hierarchy comes from size, space, grouping and surface only, within the one-weight rule.
- **The preview per platform is the value of the editor:** the text as it is posted, `[[Name]]` as a LinkedIn mention or an Instagram `@handle`, an entity without an id as plain text, an unknown `[[Name]]` as an error, every plain occurrence of an entity's name marked, the character count against the platform limit (LinkedIn 3000), the one-hour late rule, the images.
- **Autosave only where nothing can go out (updated 2026-11-26):** drafts and ideas save themselves; a planned or posted post is saved with Save. A copy in the browser guards unsaved text. **Plan is its own button.** Errors block plan, not save: a draft may be unfinished, and the sender validates again. Saving an planned post keeps it planned and shows how long until it is due.
- **Images:** dragged onto the page, written into the campaign folder, listed in `media:` in the frontmatter, thumbnails made in the browser (no `sharp` on Workers).
- **Add variant** copies text, date and images into a new file for another channel; after that they diverge (every file stands alone). A story is a variant of type `story`. Deleting a variant deletes its file.
- **Edited elsewhere:** every read returns a revision token (git blob sha, or mtime on disk) and a write sends it back; a mismatch shows "changed elsewhere" with reload or overwrite. This matters because the same files are edited in Obsidian.
- **The folder follows the title and the date (changed 2026-11-22):** the date prefix is the earliest `date` of the variants and moves with it until the first variant is `posted` or `deleted`, then it is frozen (the first version fixed it at the creation date); the slug after it is `slugify` of the campaign title (the first non-empty `title`), and every save renames the folder when it no longer matches (`syncFolder` in `src/campaign.ts`; a clash gets `-2`; an empty title keeps the folder). It moves the images, the `.state` files and the `post:` of an idea (`relinkIdeas`), refuses while a variant is `posting` or `unconfirmed`, and the save answer carries the new `folder` so the editor reloads on the new URL. Why: the folder name is what the user sees in the content repo and in Obsidian.
- **Logic stays in `src/`:** one pure, tested function takes the raw file, the entities and the channel and returns the preview segments and the errors; it also runs in the browser. The behaviour (live preview, `[[` completion) is a plain script, no framework until it outgrows that. Storage goes through a `ContentStore` (read, write with a revision token, delete; a file implementation first, a GitHub one later), like `StateStore`.
- **Not building:** rich text, autosave, AI text, best-time suggestions, comments or approval flows.
- **Slices, all built:** a read-only post page with the preview; editing and saving to disk; the chips and plan; images; add and delete variants; the edited-elsewhere check; `[[` completion. What the sections below call a slice number is only history.
- **Slice 1 is built:** `/posts/<folder>` and `/posts/<folder>/<variant>` (a rest route, `app/pages/posts/[...path].astro`) show one campaign read-only: variant tabs, chips (date, status, `manual`, images), the file as it is on disk, and the preview per platform. Every card in the list and every month chip links there (`postHref`). The loader is `loadCampaign(root, folder)` in `src/campaign.ts`: it only accepts a folder that exists directly under `posts/` (so no path from the URL ever reaches the disk), lists every variant even when its file does not parse (error plus raw preview), and adds the provider's problems. `preview()` in `src/preview.ts` is pure and shares its mention matching with the LinkedIn sender (`mentionSegments`, which `littleText` uses too), so the preview cannot drift from what is posted. The parse error stays the authority; the preview only reports what it needs to render (unknown entity, no id for the platform, over the limit).
- **Slices 2 and 3 are built: one model, two views.** The raw file text is the only model; the page has a toggle between **Edit** and **Source** (the choice is remembered). Source is the whole file (frontmatter and text) in one monospace textarea. Edit hides the frontmatter and shows fields instead: a `datetime-local` date, the `manual` checkbox, the status chip with Approve or Back to draft, and the text. Every change in Edit writes back into the raw text through `src/frontmatter.ts` (`withBody`, `withDate`, `withManual`, `withStatus`; `setFrontmatter` edits the YAML document, so other keys, their order, comments and flow lists like `images: [a.jpg]` stay as they are, and `manual: false` removes the key). Switching to Edit re-reads the text; if the frontmatter does not parse it stays in Source with the reason ("Frontmatter: unterminated frontmatter"). A file without valid frontmatter can still be fixed and saved as a draft. The preview updates as you type, in the browser, from `preview()` (the pure wikilink code lives in `src/mentions.ts` so no `node:fs` reaches the bundle).
- **Saving:** `POST /api/posts/<folder>/<variant>` with `{ raw, revision }` (`app/pages/api/posts/[...path].ts`) calls `saveVariant` (`src/campaign.ts`), which writes exactly that text through a `ContentStore` (`src/content-store.ts`: `read` and `write(path, text, expectedRevision)`; the file implementation writes atomically and only accepts paths shaped `posts/<folder>/<file>.md`). The revision is the sha1 of the file text; a write with an old revision throws `RevisionConflict` (409): nothing is written, the page says the file changed elsewhere and keeps the typed text (slice 6: the 409 answer carries the file's current revision; Reload drops the typed text and reloads the page, Overwrite sends the typed text again with that revision; Overwrite is left out when the save came from the Approve buttons, which roll back). The response carries the new revision, the re-read problems and the due time, so the red box and the status line update after a save. Line endings in a saved file become `\n`.
- **Planning is checked on the saved text, wherever it was typed** (`PlanBlocked`, HTTP 422): when the text becomes `status: planned` and the file was not, it must parse, have no provider problems, and unless it is `manual` its date may not be more than an hour in the past (it would be skipped as late). A blocked save writes nothing and shows the problems; the Approve button rolls its change back, in Source the typed text stays. Saving an already planned post is not checked again: it stays planned, and the status line says what happens next ("Planned. It posts automatically in 2 d 12 h." or, for a reminder, "Planned. You get a reminder on Fri 20 Nov, 12:00 and post it yourself.").
- **Mentions (slice 7, built).** In **Edit** you type `@` and a list of entities opens under the cursor; the `[[ ]]` syntax is only visible in **Source**, where typing `[[` opens the same list. Edit shows every known `[[Name]]` as `@Name` and writes `@Name` back as `[[Name]]` (`toEdit` and `fromEdit` in `src/mentions.ts`): the `@` must start a word (so `the PoPPo contact address` stays), the longest entity name wins, matching ignores case and the file's spelling is used, an unknown `[[Name]]` keeps its brackets in Edit so it is not lost, and a literal `@Name` for a known entity becomes a link on the first edit. Nothing is rewritten until you type, so opening a post never changes the file. The list (`app/scripts/autocomplete.ts`, matching in `suggest` and `triggerAt`) sorts names that start with the query first, shows one mark per entity, for the platform of the variant being edited (dimmed when the entity has no id for it; none on Facebook, which has no ids), takes arrows, Enter or Tab, Esc, and the mouse, and is placed at the caret with a hidden mirror of the textarea. Other platforms refuse it through their own image checks. A cover carries a small dark "PDF" chip at its bottom left (`isCover` in `src/types.ts` recognises the `.pdf.cover.jpg` name; the editor tile and preview, the List thumbnail and the peek card), so it does not pass for a plain image; the chip is text only, no icon. A PDF added before covers existed has no cover until it is added again. Video is not built.
- **Images (slice 4, built).** In Edit, under the text: a strip of thumbnails with move earlier, move later and remove buttons (buttons, not drag-reorder, so it works by keyboard), an "Add images" file input and drop onto the Write panel. An upload goes at once to `PUT /img/<folder>/<file>` (`saveImage` in `src/media.ts`, through `ContentStore.writeFile`): the content is sniffed (JPEG, PNG, GIF, WebP; the extension follows the content), at most 10 MB, the name is cleaned, the same content under the same name is reused and a different file gets `-2`, `-3`. Listing the image in the frontmatter is part of the text and is saved with Save, so one save is still one commit. Remove only unlists: the file stays, because variants may share it. Files are not renamed or numbered on purpose: the order lives in `media:`, and a rename breaks other variants, Obsidian links and history. Orphaned files are not cleaned up.
- **Ideas (built 2026-11-19, v1):** `ideas/<date>-<slug>/idea.md` in the content repo, one folder per idea (`title`, optional `link`, `status`: missing is new, then `approved` or `made` (a post was created from it; the name says so on purpose, because the idea does not follow the post's own status); `post:` names the post made from it; the body is the notes). `/ideas` is one grid of cards with a status chip each (a single image fills the card width, proportional and at most 24 rem tall; two or more are a fixed three-column grid in their own proportions, `+N` on the third; the link row is left out when the title already is the link's domain), under an add field and a row of filter chips shaped like the variant tabs on the post page (Open, Approved and Made, each with a coloured dot and a count; the buttons use `data-show`, never `data-filter`, which is the sidebar's channel filter) (a pasted address becomes the link and the domain the title, `titleFrom`) and one button per step: Delete and Approve, Unapprove and Make post. The store accepts `ideas/` next to `posts/`. **Not built, planned in this order:** the Telegram bot (a webhook on `/api/telegram/…`, open to the login but checked with Telegram's secret token and an allowlist of chat ids, text becomes the idea, a URL the link, a photo an image, the bot answers with the card), link previews (fetch Open Graph title, description and image once at save time and store them with the idea; the server must refuse private addresses, follow few redirects and cap time and size because the app is public), images on ideas.

- **Title (built).** `title:` is an optional frontmatter key (text) in any variant file. The campaign title is the first variant with a non-empty `title` (files in name order), otherwise the folder name made readable (`folderTitle` in `src/text.ts`: date off, hyphens to spaces, first letter capital). The page header is an input that edits the `title` of the variant on screen (`withTitle`, saved with the normal Save; an empty field removes the key); `New post` writes the title as typed, with its capitals and punctuation, while the folder stays a slug of it and never changes. The app reads the local token file for it (`app/lib/data.ts`). A channel with a problem shows "Not connected" (reason in the tooltip) in the sidebar, in New post and in the add variant list, and stays usable for `manual` posts and for planning. Planning a post that is not `manual` for such a channel is blocked like any other planning problem (`saveVariant`'s `connection` argument; saving an already planned post is not checked again). In a hosted version the token lookup changes, the rule stays.
- **Connecting in the browser (built, LinkedIn person channels only).** The app is for people who use a browser, never a terminal: nothing the UI says may refer to a command. The sidebar has a `Channels` link (the heading above the filters on the calendar views, a plain link elsewhere) to `/channels`: every channel with its status (token and expiry, or the reason it cannot post) and a Connect or Reconnect button for LinkedIn person channels (`connectProblem` in `src/connect.ts`). Below the list a "LinkedIn app" block walks through three steps: copy the redirect URL (`<app origin>/channels/callback`) into the LinkedIn app under Auth, paste the client ID and secret (saved in `~/.config/social/apps.json` or `$BOMBARIE_APPS`, mode 600, `src/apps.ts`; the secret is never shown again), press Connect. The redirect URL differs per origin you open the app on (`localhost` vs `127.0.0.1`); the page shows the one in use. Untested against LinkedIn itself (the unit tests mock it). Local only: the app has no login.
- **Browser safety net:** unsaved text is kept in `localStorage` per variant. A page always starts clean: a kept copy with the same revision is only offered (a `Restore it` button and the line "Unsaved text from your last visit was kept."), never applied silently, so a crash or a power cut loses nothing and a stale copy can never make the page dirty on its own. A `Discard changes` button next to Save shows whenever the page is dirty and returns to the saved file. `beforeunload` warns on a dirty page (not on `form[data-leave]` submits); Ctrl or Cmd S saves.

- **Limits:** the API has no authentication, so the app must only run locally (it already must not be hosted without a login). `loadCampaign` still reads through `node:fs`; the GitHub store will need it to read through the `ContentStore` too. The upload route has no authentication either.

On LinkedIn the later parts are comments under the post (`POST /rest/socialActions/{urn}/comments` with `actor`, `object`, `message.text`, built 2026-11-24 from the Comments API page, never run against LinkedIn): the page lists `w_member_social_feed` for commenting, which this app has not asked for, so a refusal (403) comes back as a warning. Buffer and Postiz do post LinkedIn comments, with their own approved apps. Up to 10 comments of 1250 characters.
- **4px grid (2026-11-24):** the root font size was 106.25 % (17 px text), so every `rem` spacing was 6.25 % too big and the 16/32/48 rhythm was really 17/34/51 (a small button was 34 px). The root size itself was left in place then, which kept every font size off the scale (12.75, 14.875, 19.125, 25.5, 34 px); it is gone since 2026-11-27: the root is the browser's 16 px, so text is 12, 14, 16, 18, 24 and 32 px, and `src/spacing.test.ts` refuses a root font size. `--spacing: 4px` in `app/styles/global.css` puts every Tailwind gap, padding and size on the grid (`gap-4` is 16 px); the controls (`--control-sm/md/lg` in the `social` theme) are 32/40/48 px; the named spacings in `ui` (`tight`, `close`, `related`, `moment`, `section`) are px. Type, radii, breakpoints and the width caps stay in `rem`. `src/spacing.test.ts` checks the `--spacing` line, but only reads class names, so a measured size in the browser is still the truth. `scroll-mt-[17rem]` in `DayCell` was tuned by eye against the old scale.
- **Image and compose (2026-11-25, not run on GitHub yet):** `.github/workflows/image.yml` runs `pnpm test` and `pnpm typecheck` on every push and pull request, and on `main` and `v*` tags builds a `linux/amd64` and `linux/arm64` image (an Oracle Ampere VPS is arm64) and pushes it to `ghcr.io/<owner>/<repo>` as `latest`, `sha-…` and the semver tag. `docker-compose.yml` names that image and also has `build: .`, so `docker compose up --build` builds locally; `.env.example` lists the three variables (`BOMBARIE_USERS` is required, the Telegram pair is optional); `data/` and `config/` are the two volumes to back up. A first start from empty folders works (checked 2026-11-25 by serving the build against empty `data` and `config`: every page answers 200); `channels.yml` is created by the first Add channel. `packageManager` in `package.json` pins pnpm for both Corepack in the Dockerfile and `pnpm/action-setup`.
- **Labels (2026-11-25, one line):** the label of an input or a row is regular weight `text-sm text-ink-soft` (`Field` for forms, `ActionRow` for the Post block, the Post and Comment labels in the editor). The bold `Heading variant="label"` is for the heading of a group of things (Channels, Unused in this post), never for the label of one input.
- **State beside the post and no public folder (2026-11-25):** everything that belongs to a post lives in its folder: the markdown (your intent), `<variant>.state.json` (what the app did: status, remote id, url, who, the posted replies and their ids) and the media. The state is not in the markdown because the editor would hit a revision conflict at every write and the Source view would let you delete it by accident (and so post twice). Meta gets pictures and videos through signed addresses served from the post folder, so no copies exist and a deleted post is gone at once. The signature changes when `BOMBARIE_USERS` changes, which only breaks addresses that are being fetched at that moment. Migration for existing data: a script that moves `.state/<folder>/<variant>.md.json` to the post folder (dry run first); `.public/` can be deleted. Unverified against Meta: a real Instagram or Threads post with a picture and a video through the new address.
- **One content folder (2026-11-25):** everything that is yours lives in `data/` (posts, ideas, entities, `channels.yml`, avatars, feed items in `.state/_feeds`), gitignored in the product repo, so the repo holds code only and a commit needs no exclusions. The app reads `BOMBARIE_ROOT` and defaults to `./data`; in Docker it is `/data`, the volume `./data` in `docker-compose.yml`. Tokens and app secrets stay in `config/`, outside the content folder, so it can be a git repo of its own. The git history still contains the content that was committed before this change; publishing the code needs a fresh repository or a rewritten history.
- **Encrypted tokens and app keys (2026-11-25):** `config/tokens.json` and `config/apps.json` hold one sealed object `{v, salt, iv, tag, data}` (`src/vault.ts`): AES-256-GCM, key = scrypt of `BOMBARIE_SECRET` with a salt per file (the derived key is cached per process), authenticated so a wrong secret or a damaged file is refused with one message. A plain file is refused too ("not encrypted"), without a fallback: existing files are encrypted once with a script (`encrypt-secrets.mjs`: `dry`, `apply`, `check`; it lives outside the app, in the notes of the migration). In production the app does not start the first time it needs a secret without `BOMBARIE_SECRET`; in development a fixed development key is used so nothing needs setting. What this protects: a backup or copy of `config/` alone. Whoever has the container's environment too can read the tokens; that is the usual limit without an external key vault. Passwords in `BOMBARIE_USERS` are not hashed on purpose: sign-in with GitHub is meant to replace them. Losing the secret means connecting the channels again.
- **Sign-in with GitHub (2026-11-25, replaces `BOMBARIE_USERS` and every password):** an OAuth app, not a GitHub App, because only the user name is needed and the repository access of the git sync is a separate decision. `/login/github` sets a `state` cookie (httpOnly, path `/login/github`, 10 minutes) and sends you to GitHub with no scopes; `/login/github/callback` checks the state, exchanges the code (`src/github-login.ts`), reads `GET /user` for the login, and throws the GitHub token away, so nothing is stored. Only the names in `BOMBARIE_ADMINS` (case ignored) get the session cookie, the same signed cookie as before, now signed with `BOMBARIE_SECRET`, so the session name and the `by` on actions are the GitHub login. Without `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` and `BOMBARIE_ADMINS` the app is open in development and answers 503 in production. No password fallback on purpose: if GitHub or the OAuth app is wrong you are locked out and fix the three variables on the server.
- **No `.env` (2026-11-25):** the GitHub OAuth app, the users and the key live in `config/`, set up in the app. `config/apps.json` (encrypted) holds the `github` app next to the platform apps and a `users` map (`name: admin|member`, `src/users.ts` holds the rules: an admin adds and removes, the last admin stays, a typed name is checked at GitHub before it is stored, `Users` page for admins). The key is `BOMBARIE_SECRET` when set, else `config/secret.key`, made once with mode 600 (so a copy of the whole folder is readable; the variable is for people who want the key elsewhere). First start: with no owner, `/setup` is open for 15 minutes after the process started (a hijack gets an empty installation and shows at once: the real owner finds it set up), takes the OAuth client ID and secret, and the first GitHub account that signs in becomes owner; after 15 minutes `/setup` says it is closed until the container restarts. A session counts only while the name is still in `users`, so removing someone takes effect on their next request. Telegram is still two optional variables; moving them into a Settings page is the last step to no variables at all.
- **Telegram in the app (2026-11-25):** the bot token and chat id are two entries in the encrypted `settings` of `config/apps.json` (`telegramToken`, `telegramChat`), set on the Settings page (admins; `app/lib/telegram.ts` reads them for the scheduler, the webhook route and the reminder switch in the post editor). Saving registers the webhook at once when the page is served over https; both fields empty turns Telegram off. No environment variable is needed any more.
